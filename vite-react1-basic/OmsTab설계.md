정확한 통찰입니다! `kdy987`님이 느끼신 대로 **HyperPane**은 전체 판을 짜는 **Workspace(관리자)** 역할을 하고, 그 안에서 실질적인 화면 전환을 담당하는 **OmsTab**이 핵심 부속이 되는 구조가 가장 이상적입니다.

넥사크로의 MDI(Multi Document Interface) 구조를 React 스타일로 현대화한 **HyperPane 아키텍처**를 제안해 드립니다.

---

## 🏗️ HyperPane 전반적 설계안

전체 시스템은 **'상태(Data)' -> '레이아웃(Frame)' -> '구성 요소(Component)'** 순으로 계층화됩니다.

### 1. 계층 구조 (Hierarchy)

* **HyperPane (Root Container)**:
* 전체 워크스페이스의 상태(어떤 탭이 열려 있는지, 현재 활성 탭은 무엇인지)를 관리합니다.
* `Zustand` 같은 상태 관리 도구를 사용해 "창 분할 상태"를 저장합니다.


* **OmsTabGroup (Navigation)**:
* 상단에 나열된 탭들의 묶음입니다.
* 여기서 우리가 만든 `OmsIconButton`을 사용해 '새 탭 추가', '전체 닫기' 등을 수행합니다.


* **OmsTab (Item)**:
* 개별 탭 버튼입니다. 클릭 시 활성화되며, `x` 버튼으로 닫기 기능을 가집니다.


* **PaneArea (Content Renderer)**:
* 현재 활성화된 탭의 컨텐츠(예: 주문관리, 통계차트)가 실제로 렌더링되는 영역입니다.
* 분할 모드일 경우 두 개의 `PaneArea`가 나타납니다.



---

### 2. 컴포넌트 설계 (Props 중심)

범용성을 고려하여 각 컴포넌트가 가질 핵심 속성들입니다.

| 컴포넌트 | 핵심 Props | 역할 |
| --- | --- | --- |
| **HyperPane** | `layout: "single" | "split"` |
| **OmsTab** | `id, title, isActive, isClosable` | 탭의 상태 표시 및 이벤트 전달 |
| **OmsTabGroup** | `tabs: TabItem[], activeTabId` | 탭 리스트 렌더링 및 드래그 앤 드롭 정렬 |

---

### 3. 데이터 흐름 (State Management)

넥사크로에서는 전역 변수나 Dataset을 썼겠지만, 여기서는 **Zustand** 스토어를 하나 만들어 관리하는 것이 '버거움'을 줄이는 비결입니다.

```typescript
// hyperpane-store.ts (개념 예시)
interface Tab {
  id: string;
  title: string;
  component: React.ReactNode; // 실제로 보여줄 화면
}

const useHyperPane = create((set) => ({
  openTabs: [],
  activeTabId: null,
  addTab: (newTab) => set((state) => ({ 
    openTabs: [...state.openTabs, newTab],
    activeTabId: newTab.id 
  })),
  // ... 탭 닫기, 탭 위치 변경 로직 등
}));

```

## 💡 왜 이렇게 설계해야 할까? (생산성 포인트)

1. **재사용성**: `OmsTab`은 독립적인 컴포넌트이므로, 나중에 브라우저 탭 스타일뿐만 아니라 카드 스타일, 세로 메뉴 스타일 등으로 디자인만 바꿔서 재사용하기 좋습니다.
2. **확장성**: `kfs2025` 프로젝트 도중 "탭을 분리해서 새 창으로 띄워달라"는 요구가 와도, `HyperPane`의 상태 로직만 수정하면 UI는 그대로 유지할 수 있습니다.
3. **유지보수**: 탭의 모양을 고치고 싶으면 `OmsTab.tsx`만, 탭이 열리는 로직을 고치고 싶으면 `useHyperPane` 스토어만 보면 됩니다.

## 🚀 다음 실행 단계 제안

설계가 나왔으니, 가장 작은 단위부터 조립해 보는 게 좋겠죠?

**"OmsTab" 컴포넌트를 먼저 코딩해 볼까요?** 이전에 만든 `OmsIconButton`의 로직을 응용해서, **[아이콘 + 제목 + 닫기버튼]**이 합쳐진 형태를 만들어보면 재미있을 것 같습니다.

`OmsTab` 코딩을 시작해 볼까요, 아니면 전체적인 레이아웃 구조에 대해 더 궁금한 점이 있으신가요?


매우 날카롭고 합리적인 지적입니다. 개발자로서 가장 경계해야 할 것이 바로 **'이미 있는 바퀴를 다시 만드는 것(Reinventing the wheel)'**이죠.

결론부터 말씀드리면, **"단순한 탭"**은 이미 널려 있지만, 우리가 목표로 하는 **"HyperPane(MDI + 분할 창 + 상태 유지)"**은 기성품만으로는 해결이 안 되는 영역이 분명히 존재합니다. 세 가지 관점에서 냉정하게 분석해 드릴게요.

## 1. react-router-dom으로 가능한가?

가장 간단한 방식이지만, 우리가 원하는 **MDI(다중 문서 인터페이스)**와는 목적이 다릅니다.

* **Router 방식**: URL이 `/orders`에서 `/users`로 바뀌면 이전 화면(`orders`)은 메모리에서 사라집니다. 뒤로 가기를 해야만 볼 수 있죠.
* **HyperPane 방식**: 엑셀처럼 여러 시트를 열어두고 수시로 왔다 갔다 하며, **입력하던 데이터가 그대로 남아 있어야 합니다.**
* **결론**: `react-router-dom`은 단순 페이지 이동용입니다. `kfs2025` 같은 복잡한 관리자 시스템에서 요구하는 **"여러 화면 동시 유지"**에는 맞지 않습니다.

## 2. Open Source 라이브러리가 있지 않은가?

`react-tabs`나 shadcn/ui의 `Tabs` 컴포넌트가 있습니다. 하지만 이들은 보통 **한 화면 내의 내용 전환**용이지, **브라우저 전체의 탭 시스템**을 구축하기엔 기능이 부족합니다.

우리가 구현하려는 기능 중 오픈소스가 제공하지 않는 것들:

* **창 분할(Split View)**: 한 탭을 오른쪽으로 던져서 두 화면을 동시에 보는 기능.
* **동적 추가/삭제**: 사용자가 메뉴를 클릭할 때마다 탭이 생성되고 닫히는 로직.
* **영속성(Persistence)**: 새로고침해도 열려있던 탭들이 그대로 복구되는 기능.

## 3. 그럼 왜 직접(또는 래핑해서) 만드는가?

우리는 **"밑바닥부터 코딩"**하는 것이 아니라, **"오픈소스 로직을 조립"**하려는 것입니다.

* **탭 레이아웃**: shadcn/ui의 `Tabs`나 `Buttons`를 활용 (디자인 생략)
* **창 분할**: `react-resizable-panels` 라이브러리 활용 (복잡한 수학 계산 생략)
* **상태 관리**: `Zustand` 활용 (데이터 흐름 자동화)

즉, 우리가 하려는 작업은 **"부품을 직접 깎는 것"**이 아니라, **"기성 부품들을 HyperPane이라는 설계도에 맞춰 조립하는 것"**에 가깝습니다.

## 💡 구현해야 할 실질적인 이유 (Justification)

만약 아래 조건 중 2개 이상이 해당된다면, 우리가 구상하는 수준의 구현은 반드시 필요합니다.

1. **데이터 보존**: 탭 A에서 주문서를 작성하다가 탭 B에서 고객 정보를 확인하고 다시 A로 왔을 때 데이터가 그대로 있어야 함.
2. **멀티태스킹**: 왼쪽에는 게시판, 오른쪽에는 상세 보기창을 띄우는 식의 사용자 정의 분할이 필요함.
3. **넥사크로 경험**: 기존 사용자들이 MDI 방식(열려있는 화면 목록)에 익숙함.
